## libuv

Tu JavaScript corre en un solo hilo, pero Node.js no hace todo en ese hilo. **libuv**, la librería en C que está debajo, se encarga de la entrada y salida:

- La **red** la atiende el sistema operativo, que avisa cuando hay datos.
- Los **archivos**, la criptografía pesada y la compresión los hace un grupo de hilos auxiliares (cuatro por defecto).

Cuando una operación termina, libuv deja su callback en la cola de la fase que corresponde.

## Las fases

Cada vuelta del event loop recorre estas fases, en orden:

| Fase | Qué callbacks corren |
|---|---|
| **timers** | Los de `setTimeout` y `setInterval` cuyo tiempo venció |
| **pending callbacks** | Algunos errores de sistema que quedaron pendientes |
| **poll** | Los de entrada y salida: datos de red, archivos leídos… Si no hay nada que hacer, el loop espera aquí |
| **check** | Los de `setImmediate` |
| **close** | Los de cierre, como `socket.on("close")` |

Y entre **cada** callback, de cualquier fase, Node.js vacía dos colas prioritarias:

1. La de **`process.nextTick`**.
2. La de **microtareas**: promesas y `queueMicrotask`.

## setImmediate o setTimeout

Como muestra el pizarrón, dentro de un callback de entrada y salida, `setImmediate` corre **antes** que `setTimeout(…, 0)`: la fase check viene justo después de poll, y timers espera a la vuelta siguiente.

Desde el programa principal, en cambio, el orden entre los dos **no está garantizado**: depende de cuánto tardó el loop en arrancar. No escribas código que dependa de ese orden.

## nextTick: con cuidado

`process.nextTick(fn)` corre `fn` apenas termine la operación actual, antes que cualquier promesa y que cualquier fase. Se usa, por ejemplo, para que una función siempre llame a su callback de forma asíncrona.

Pero su prioridad es un arma de doble filo: un `nextTick` que se agenda a sí mismo en bucle **nunca deja avanzar** al event loop. Para "hacer algo después", prefiere `setImmediate` o `queueMicrotask`.

<Nota tipo="ojo">
  En un módulo **ESM**, todo el archivo se evalúa dentro de una microtarea. Por eso, en el nivel superior de un `.mjs`, una promesa ya resuelta corre **antes** que un `process.nextTick`, al revés que en CommonJS. Es una trampa conocida: el orden de los ejemplos de esta lección es el de un archivo `.cjs`.
</Nota>

## No bloquees el hilo

En un servidor, el único hilo atiende **todas** las peticiones. Si una petición hace algo síncrono y lento, las demás esperan:

```js
import http from "node:http";
import { readFileSync } from "node:fs";
import { readFile } from "node:fs/promises";

http.createServer(async (req, res) => {
  // ✗ Bloquea: mientras lee, nadie más es atendido
  // const html = readFileSync("pagina.html", "utf8");

  // ✓ No bloquea: libuv lee el archivo y el hilo sigue atendiendo
  const html = await readFile("pagina.html", "utf8");
  res.end(html);
}).listen(3000);
```

Lo mismo con cálculos pesados (cifrar, comprimir, procesar imágenes, un JSON enorme): o las versiones asíncronas de Node, o un **worker thread**, el próximo tema.

## Resumen

- **libuv** hace la entrada y salida (la red con el sistema operativo y los archivos con un grupo de hilos) y avisa con callbacks.
- El loop recorre fases: **timers → poll → check → close**.
- Entre cada callback se vacían la cola de `nextTick` y, después, la de microtareas.
- Dentro de un callback de I/O, `setImmediate` gana a `setTimeout(…, 0)`; desde el programa principal, el orden no está garantizado.
- Nunca bloquees el hilo en un servidor: usa las APIs asíncronas o workers.
