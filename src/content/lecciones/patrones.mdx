## En serie, en paralelo y en un forEach

```js
const esperar = (ms, valor) => new Promise((r) => setTimeout(() => r(valor), ms));
const ids = [1, 2, 3];

// En serie: una tras otra (cuando cada paso necesita el anterior)
const enSerie = [];
for (const id of ids) {
  enSerie.push(await esperar(20, id));
}

// En paralelo: todas a la vez
const enParalelo = await Promise.all(ids.map((id) => esperar(20, id)));

console.log(enSerie, enParalelo);
```

<Nota tipo="error">
  `ids.forEach(async (id) => await algo(id))` **no espera a nada**: `forEach` ignora las promesas que devuelve el callback y termina enseguida. Usa `for...of` con `await` (en serie) o `Promise.all` con `map` (en paralelo).
</Nota>

## Concurrencia limitada

`Promise.all` lanza **todo a la vez**. Con mil pedidos, eso puede saturar un servidor o el navegador. La solución: un número fijo de "trabajadores" que toman tareas de una fila común.

```js
const esperar = (ms, valor) => new Promise((r) => setTimeout(() => r(valor), ms));

async function conLimite(tareas, maximo) {
  const resultados = [];
  let siguiente = 0;
  let enCurso = 0;
  let pico = 0;

  async function trabajador() {
    while (siguiente < tareas.length) {
      const i = siguiente++;
      enCurso++;
      pico = Math.max(pico, enCurso);
      resultados[i] = await tareas[i]();
      enCurso--;
    }
  }

  await Promise.all(Array.from({ length: maximo }, trabajador));
  console.log("como máximo a la vez:", pico);
  return resultados;
}

const tareas = [1, 2, 3, 4, 5, 6].map((n) => () => esperar(20, n * 10));
console.log(await conLimite(tareas, 2));
```

Las tareas son **funciones** que devuelven promesas, no promesas: así no empiezan hasta que un trabajador las toma.

## Reintentos con backoff

Las operaciones de red fallan a veces por motivos pasajeros. Reintentar ayuda, pero sin martillar: entre intento e intento, se espera **cada vez más** (100 ms, 200, 400…). Lo vas a escribir en el laboratorio.

## Límite de tiempo

Ya lo viste con `Promise.race` y con `AbortSignal.timeout`. La segunda opción es mejor cuando la operación acepta una señal, como `fetch`, porque además la **cancela**:

```js
// Con race: deja de esperar, pero la operación sigue
// Con una señal: deja de esperar y la operación se detiene
fetch(url, { signal: AbortSignal.timeout(5000) });
```

## Debounce

Un **debounce** retrasa la ejecución hasta que pasa un tiempo **sin** nuevas llamadas. Ideal para buscar mientras el usuario escribe:

```js
function debounce(fn, ms) {
  let id;
  return (...args) => {
    clearTimeout(id);                         // cada llamada cancela la anterior…
    id = setTimeout(() => fn(...args), ms);   // …y programa una nueva
  };
}

const guardar = debounce((texto) => console.log("guardado:", texto), 50);
guardar("h");
guardar("ho");
guardar("hola");  // solo esta se guarda
```

## Throttle

Un **throttle** deja pasar como máximo una ejecución cada cierto tiempo, aunque lo llamen sin parar. Ideal para el scroll o el redimensionado de la ventana:

```js
function throttle(fn, ms) {
  let ultimo = 0;
  return (...args) => {
    const ahora = performance.now();
    if (ahora - ultimo >= ms) {
      ultimo = ahora;
      fn(...args);
    }
  };
}

const registrar = throttle((n) => console.log("posición", n), 30);
let n = 0;
const id = setInterval(() => {
  registrar(++n);           // se llama cada 5 ms…
  if (n === 20) clearInterval(id);
}, 5);                      // …pero registra como mucho cada 30 ms
```

## Resumen

- **En serie** con `for...of` y `await`; **en paralelo** con `Promise.all`. Nunca `await` dentro de `forEach`.
- **Concurrencia limitada**: unos pocos trabajadores toman tareas de una fila común.
- **Reintentos** con espera creciente (*backoff exponencial*).
- **Límites de tiempo**: mejor con `AbortSignal.timeout`, que además cancela.
- **Debounce**: una ejecución cuando las llamadas se detienen. **Throttle**: como máximo una cada cierto tiempo.
