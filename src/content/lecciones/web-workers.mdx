## Un worker

El worker es un archivo aparte. Recibe mensajes, trabaja y responde:

```js
// primos.js: corre en otro hilo
self.addEventListener("message", (e) => {
  const hasta = e.data;
  const primos = [];
  for (let n = 2; n <= hasta; n++) {
    if (primos.every((p) => n % p !== 0)) primos.push(n);
  }
  self.postMessage(primos.length);
});
```

```js
// main.js: en la página
const worker = new Worker(new URL("./primos.js", import.meta.url), { type: "module" });

worker.addEventListener("message", (e) => {
  mostrar(`Hay ${e.data} primos`);
});
worker.addEventListener("error", (e) => console.error("falló el worker:", e.message));

worker.postMessage(200_000);   // la página sigue respondiendo mientras tanto
```

Con `{ type: "module" }`, el worker puede usar `import`. Para detenerlo: `worker.terminate()` desde la página, o `self.close()` desde adentro.

## Qué puede y qué no

Un worker tiene casi todo el lenguaje y muchas APIs: `fetch`, temporizadores, `IndexedDB`, `WebSocket`, `crypto`, `OffscreenCanvas`… Pero **no tiene DOM**: ni `document`, ni `window`, ni acceso a la página. Todo lo que tenga que verse, lo hace la página con los resultados que recibe.

## Mensajes: copiar o transferir

Lo que envías con `postMessage` se **copia** con la clonación estructurada, la misma de `structuredClone`: funcionan los objetos, arrays, fechas, `Map`, `Set` y arrays tipados, pero no las funciones ni los elementos del DOM.

Copiar datos grandes cuesta. Un `ArrayBuffer` (y algunos otros objetos) se puede **transferir**: la memoria pasa al otro hilo sin copiarse, y el original queda vacío.

```js
const imagen = new Uint8Array(10_000_000);   // 10 MB

// worker.postMessage(imagen.buffer, [imagen.buffer]) hace esto mismo:
const recibido = structuredClone(imagen.buffer, { transfer: [imagen.buffer] });

console.log(imagen.byteLength);     // 0: ya no es de la página
console.log(recibido.byteLength);   // 10000000: la memoria pasó entera, sin copiarse
```

## Memoria compartida: SharedArrayBuffer y Atomics

Transferir **mueve** la memoria de un hilo a otro. A veces los dos hilos necesitan ver la **misma** memoria a la vez. Un `SharedArrayBuffer` enviado con `postMessage` no se copia ni se mueve, así que la página y el worker leen y escriben los mismos bytes. Para no pisarse, se usan las operaciones de `Atomics`:

```js
// En la página
const memoria = new Int32Array(new SharedArrayBuffer(4));
worker.postMessage(memoria);   // el worker ve los mismos bytes

// Esperar un cambio sin congelar la página (ES2024)
const { async, value } = Atomics.waitAsync(memoria, 0, 0);
if (async) value.then(() => mostrar(Atomics.load(memoria, 0)));

// En worker.js
self.onmessage = ({ data: memoria }) => {
  Atomics.store(memoria, 0, 42);
  Atomics.notify(memoria, 0);   // despierta a quien espera
};
```

`Atomics.wait` bloquea el hilo, por eso la página no puede usarlo. `Atomics.waitAsync` hace lo mismo con una promesa. Por seguridad, `SharedArrayBuffer` solo existe si la página está **aislada** con las cabeceras `Cross-Origin-Opener-Policy: same-origin` y `Cross-Origin-Embedder-Policy: require-corp`. Puedes comprobarlo con `crossOriginIsolated`. Para la mayoría de los casos, los mensajes alcanzan.

## Canales propios

`MessageChannel` crea un par de puertos conectados: lo que se envía por uno llega por el otro. Sirve para darle a dos partes un canal privado:

```js
const canal = new MessageChannel();

canal.port2.onmessage = (e) => {
  console.log("port2 recibió:", e.data);
  canal.port2.postMessage(e.data.toUpperCase());
};
canal.port1.onmessage = (e) => console.log("port1 recibió:", e.data);

canal.port1.postMessage("hola");
await new Promise((r) => setTimeout(r, 20));
```

## Entre pestañas: BroadcastChannel

`BroadcastChannel` reparte mensajes entre todas las pestañas, ventanas y workers del mismo origen que abran un canal con el mismo nombre:

```js
const sesion = new BroadcastChannel("sesion");

sesion.addEventListener("message", (e) => {
  if (e.data === "cerrar") mostrarPantallaDeIngreso();
});

botonSalir.addEventListener("click", () => {
  sesion.postMessage("cerrar");   // las demás pestañas se enteran
  cerrarSesion();
});
```

<Nota tipo="consejo">
  Coordinar pedidos y respuestas por mensajes es tedioso: cada respuesta hay que asociarla a su pedido. Librerías como Comlink lo esconden, y te dejan llamar a las funciones del worker como si fueran locales, con `await`. Vas a escribir una versión pequeña en el laboratorio.
</Nota>

## Turnos entre pestañas: Web Locks

Si la persona tiene tu aplicación abierta en tres pestañas, las tres pueden intentar lo mismo a la vez: sincronizar con el servidor, renovar la sesión, migrar la base de datos local. La **Web Locks API** da turnos: solo quien tiene el "candado" con ese nombre entra, y los demás esperan:

```js
await navigator.locks.request("sincronizar", async () => {
  // solo una pestaña (o un worker) a la vez entra aquí; el resto espera su turno
  await sincronizarConElServidor();
});
// el candado se suelta solo cuando termina la función
```

Con la opción `{ ifAvailable: true }`, si el candado está ocupado la función recibe `null` en lugar de esperar: sirve para "si otra pestaña ya lo está haciendo, no lo hagas".

## Resumen

- Un **Web Worker** ejecuta código en otro hilo: la página no se congela.
- Los workers no tienen DOM; se comunican con `postMessage` y el evento `message`.
- Los mensajes se **copian** (clonación estructurada); los `ArrayBuffer` se pueden **transferir**.
- `SharedArrayBuffer` comparte memoria entre hilos; `Atomics.waitAsync` (ES2024) espera un cambio sin congelar la página.
- `MessageChannel` crea un canal privado de dos puertos; `BroadcastChannel` habla entre pestañas.
- Para pedidos y respuestas, identifica cada pedido con un `id`.
- `navigator.locks.request(nombre, fn)` da turnos entre pestañas y workers para lo que no debe correr dos veces a la vez.
