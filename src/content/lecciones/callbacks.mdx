## Avísame cuando termines

Una función asíncrona con callback recibe, además de sus datos, la función que debe llamar al terminar:

```js
function prepararCafe(tipo, alTerminar) {
  console.log(`preparando ${tipo}…`);
  setTimeout(() => {
    alTerminar(`un ${tipo} caliente`);
  }, 200);
}

prepararCafe("cortado", (cafe) => console.log("listo:", cafe));
console.log("mientras, leo el diario");
```

## Error primero

¿Cómo avisa una función con callback que algo salió mal? No puede lanzar un error, porque cuando falla ya nadie la está esperando en un `try`. Node.js popularizó una convención: el **primer argumento** del callback es el error (o `null`), y los siguientes, el resultado.

```js
function buscarUsuario(id, cb) {
  setTimeout(() => {
    if (id <= 0) cb(new Error("id inválido"));
    else cb(null, { id, nombre: "Ana" });
  }, 50);
}

buscarUsuario(7, (error, usuario) => {
  if (error) return console.log("Falló:", error.message);
  console.log("Encontré a", usuario.nombre);
});

buscarUsuario(-1, (error, usuario) => {
  if (error) return console.log("Falló:", error.message);
  console.log("Encontré a", usuario.nombre);
});
```

## Por qué try/catch no sirve

```js
try {
  setTimeout(() => {
    throw new Error("¡ups!");
  }, 0);
} catch (e) {
  console.log("Nunca llego aquí");
}
console.log("el try ya terminó");
```

Cuando el callback lanza, el `try` terminó hace rato: el callback corre en otra vuelta del event loop, con la pila vacía. El error no tiene quién lo atrape y termina el programa. Con callbacks, los errores **siempre** se pasan como argumento.

## El callback hell

Cuando cada paso depende del anterior, los callbacks se anidan:

```js
buscarUsuario(7, (error, usuario) => {
  if (error) return manejar(error);
  buscarPedidos(usuario.id, (error, pedidos) => {
    if (error) return manejar(error);
    buscarDetalle(pedidos[0], (error, detalle) => {
      if (error) return manejar(error);
      calcularEnvio(detalle, (error, envio) => {
        if (error) return manejar(error);
        mostrar(envio);
      });
    });
  });
});
```

Es la **pirámide de la perdición**: el código se desplaza a la derecha, el manejo de errores se repite en cada nivel, y hacer dos cosas en paralelo o reintentar una se vuelve muy difícil. Hay otro problema, menos visible: le entregas tu función a código ajeno y **confías** en que la llame una vez, ni cero ni dos veces. Se llama *inversión de control*.

<Nota tipo="consejo">
  Las promesas, el próximo tema, resuelven estos problemas. Si usas una API antigua de Node.js con callbacks, `util.promisify` la convierte en una que devuelve promesas, y casi todas tienen ya su versión moderna (`node:fs/promises`, por ejemplo).
</Nota>

## Resumen

- Un **callback** es una función que se pasa para que la llamen cuando la tarea termine.
- Convención **error-first**: `(error, resultado)`; mira siempre primero el error.
- `try/catch` no atrapa errores lanzados dentro de un callback asíncrono.
- Anidar callbacks lleva al **callback hell**: difícil de leer, de manejar errores y de combinar.
- Una función asíncrona debe llamar al callback **siempre** de forma asíncrona.
