## Dónde falla la herencia

La herencia modela relaciones **"es un"**. Funciona bien mientras la relación se cumple siempre, pero tiene tres problemas conocidos:

- **Un solo padre.** `extends` acepta una clase. Si un objeto necesita capacidades de dos jerarquías, no hay forma limpia.
- **Clase base frágil.** Un cambio en la clase de arriba afecta a todas las de abajo, incluso a las que no pensabas tocar.
- **Promesas que no se cumplen.** Si la hija tiene que anular un método del padre para que "no haga nada" o lance un error, la jerarquía está mintiendo. Lo vas a ver con el pingüino del detective.

## Tener en lugar de ser

La **composición** modela relaciones **"tiene un"**: un objeto se arma con piezas independientes y les **delega** el trabajo.

```js
class Motor {
  arrancar() { return "motor en marcha"; }
}

class Radio {
  encender() { return "sonando música"; }
}

class Auto {
  #motor = new Motor();
  #radio = new Radio();

  viajar() {
    return `${this.#motor.arrancar()}, ${this.#radio.encender()}`;
  }
}

console.log(new Auto().viajar());
```

Un auto no **es** un motor: **tiene** uno. Puedes cambiar el motor por uno eléctrico sin tocar `Radio` ni reorganizar ninguna jerarquía.

## Capacidades como funciones

En JavaScript, la forma más liviana de componer son funciones que **agregan una capacidad** a un objeto:

```js
const conNombre = (nombre) => ({ nombre });
const puedeCaminar = (obj) => ({ ...obj, caminar: () => `${obj.nombre} camina` });
const puedeNadar = (obj) => ({ ...obj, nadar: () => `${obj.nombre} nada` });
const puedeVolar = (obj) => ({ ...obj, volar: () => `${obj.nombre} vuela` });

const pato = puedeVolar(puedeNadar(puedeCaminar(conNombre("Pato"))));
const pinguino = puedeNadar(puedeCaminar(conNombre("Pingüino")));

console.log(pato.volar(), "·", pato.nadar());
console.log(pinguino.nadar(), "·", "volar" in pinguino);
```

Cada objeto tiene exactamente las capacidades que le corresponden. El pingüino no tiene `volar`, en lugar de tener uno que miente.

<Nota tipo="consejo">
  No es todo o nada. Un buen punto de partida: clases para las entidades del programa, **composición** para combinar comportamientos y **herencia** solo para relaciones "es un" claras y estables, como un error propio que extiende `Error`.
</Nota>

## Cómo elegir

| Pregunta | Si la respuesta es sí… |
|---|---|
| ¿La hija **es** siempre un tipo del padre, sin excepciones? | Herencia |
| ¿Necesitas combinar capacidades de varios lados? | Composición |
| ¿Tendrías que anular métodos del padre para desactivarlos? | Composición |
| ¿Quieres poder cambiar una pieza sin tocar las demás? | Composición |

## Resumen

- La herencia modela **"es un"**; la composición, **"tiene un"**.
- La herencia tiene límites: un solo padre, clase base frágil y jerarquías que no encajan con la realidad.
- Componer es armar objetos con piezas y **delegarles** el trabajo.
- Funciones como `puedeVolar(obj)` agregan capacidades sin jerarquías.
- Regla práctica: composición por defecto, herencia cuando la relación "es un" es clara.
